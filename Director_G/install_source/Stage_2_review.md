# Installing plugins, Store applications and modules

Director G, 14 November 2026. A design contribution to Director Z's [install-source study, §8](../../Director_Z/pcp_workers/install_source/GROUNDING.md). The current implementation boundary below is PCP OS source `6254a716`. The proposed operation and its tests are for Stage 2. The [executable fixture](probe_store_app.py) tests one choice of application runtime.

## What a person or machine can do

A person using the CLI or a screen and a machine using the tool server should each be able to discover, inspect, install, inspect the resulting status, and undo an installation for **all three kinds**. Both front ends call the same Rust service. A human confirmation screen is a presentation of the resolved plan. A machine with a suitable existing grant can submit the same plan directly. For both, show which target the change affects, what will run and with which rights. If the target host or account requires an interactive handoff, report that specific state with its reason and open machine-parity obligation. Only a target that accepts the authorized machine operation passes the machine-install test.

Use one package identity comprising registry/owner, kind, name, version, platform and content digest. Bind the manifest, the selected dependencies, executable modes and target entry point to verified bytes. Resolve any convenience name before committing. Bind the transaction to the expected active generation as well as the resolved package and destination. Each caller supplies a request ID. The host binds it to that actor and the resolved request, so concurrent calls, reconnections and lost replies preserve their meaning. Compare actual actor identities and decisions through both front ends. The current local module command accepts a terminal `--by` label and writes a host event identifying terminal input. A machine adapter needs its actual host-observed credential and delegated authority. A tool argument naming the principal is insufficient evidence of that authority. [Current module entry point](https://github.com/KirtusJ/pcp-os/blob/6254a71681389b1e930030591cba2823376e241f/PCP_OS_Rust/crates/pcpos-host/src/pcpos.rs#L2311)

| Kind | What counts as an installation at the named target | Separate operation |
|---|---|---|
| Module | Staged text passed the module's ID, namespace, Core compatibility and digest checks. The host enumerates and reads back that exact module. | Selecting its rules for an authorized review. |
| Store application | The host lists the verified runtime entry point under its package identity. The required runtime profile is supported and the effective privileges can be enforced. | Running the app on named inputs and reporting its output or failure. |
| Plugin | The target account or client confirms the package was installed into the intended scope. Report its observed version and digest wherever available. | Enabling it in a client or loading it into a running chat can have a separate readback. |

The index, authorization checks and event format can be shared even when the three destinations commit changes differently. The tested Claude marketplace branch is a distribution adapter. ChatGPT’s account release service owns a different destination. A file in a PCP cache alone proves neither client installation nor activation in a particular session. Where a provider only reports an ID and version, store that observed receipt and the locally verified digest as distinct fields. [Claude branch installation test](https://github.com/KirtusJ/pcp/pull/29#issuecomment-6872832738) · [ChatGPT release and native-reader scope](https://github.com/KirtusJ/pcp-os/pull/23#issuecomment-6872584824)

## Executable Store applications

For the first runtime-installable app, use a pure Science or Mathematics calculation, authored in Rust, with a fixed typed input and output. A package containing a declarative module can use the same install transaction without launching code. An executable app can be a Rust program compiled to WebAssembly in a restricted worker. Native executable packages are another profile where the launcher has a supported OS sandbox. The guest profile separates the app from the compiled-in Store without requiring a native capability implementation for every desktop in the first experiment. The freestanding kernel's existing ELF loader and capability-mediated system calls are relevant implementation precedents; a desktop child inherits its desktop host's rules. [Current built-in Store](https://github.com/KirtusJ/pcp-os/blob/6254a71681389b1e930030591cba2823376e241f/PCP_OS_Rust/crates/pcpos-host/src/instruments.rs#L18) · [Kernel system calls](https://github.com/KirtusJ/pcp-os/blob/6254a71681389b1e930030591cba2823376e241f/PCP_OS_Rust/crates/pcpos-kernel/src/sys.rs#L1) · [Wasmtime security](https://docs.wasmtime.dev/security.html)

The signed manifest states requested rights. The host computes effective rights from those requests, caller delegation and destination policy. A necessary right that cannot be granted should identify the unsupported operation. At run time only the granted handles are exposed, preferably for the specific input or output object and operation. For a pure calculation the caller can pass the input value and accept a bounded result. For a future evidence-reading app, supply the approved snapshot handle with its digest and cutoff. Raw register write access would let an app alter the evidence of its own execution. The host observes and writes the installation record. If a new version requests wider rights, resolve the new rights under the current policy for the actual actor.

On Windows x64, a normal child process in a fresh working directory could read a named sibling file. The file was a disposable fixture. Using the Wasmtime 50.0.1 Python interface to the Rust engine, a guest with no imports returned 42 for $7\times6$. Attempts to import file-open and socket-accept operations failed at instantiation. Growth past one 64 KiB guest memory page returned failure, and an infinite guest loop exhausted the assigned fuel. These outcomes test the stated imports and two resource controls. They do not establish isolation of arbitrary native plugins, host callbacks, the compiler, or all engine resources. For the pilot, compile and validate uploaded bytes under bounded resources; keep fetch, compilation, guest execution and target callbacks outside the register lock. Host calls that wait on I/O need their own cancellation and exit observations. ## Install, retry and undo

Fetch into bounded staging. Verify and retain the exact bytes to be activated. Under the destination's mutation protocol, recheck the active generation, authority and resolved plan, and durably record the intent before activation. Record a complete installation only after destination readback. A local publisher can atomically replace its active-generation pointer and then reconcile the register with that pointer after a crash. An external provider has its own transaction boundary. If its reply was lost, reconcile through a provider request key, receipt or authoritative target query. When the query cannot disambiguate a previous effect, retain the indeterminate outcome. A blind retry can duplicate an external effect.

Undo is another authorized transaction naming the expected current generation and the previous activation. Preserve the original records and any packages shared by other installs. Verify what the destination actually restored and retain any irreversible effects of an earlier app run. Rechecking a proposed rollback against current revocation and local policy prevents an old activation receipt from silently restoring a now-disallowed executable. The same rules and readback apply when a machine initiates undo. A user who has the authority to undo a machine installation should be able to find it by actor, target and request ID.

## Stage 2 acceptance run

1. In a disposable destination, install a pinned module, a pure app and a plugin, first through the person entry point and then through the machine entry point from identical starting state. Compare resolved package, scope, effective rights, destination state and receipt fields. The authenticated initiator must differ. With equivalent grants, expected decisions and side effects agree. Include an authorized unattended installation as a positive control and deny an attempt to claim another actor's stronger grant.
2. Repeat requests both in sequence and concurrently. Reusing a request for different content must be distinguishable from retrying the identical request. Change the target generation, capability grant or staged bytes after preview, and verify that the stale plan cannot silently commit the changed effect.
3. Interrupt before activation, after local pointer replacement, after an external provider accepts but before its reply, and after readback but before the final register append. Reopen the transaction through the other front end. Compare the final evidence with the actual destination. Exercise undo from both front ends, including a newer claimant to the same target. Preserve an unresolved outcome when the provider cannot establish which effect occurred.
4. Show a valid module remains readable without selecting it for a review. Show an app becomes available without executing an installer hook; explicitly exercise its permitted calculation and refused access. For each supported plugin target, test actual installation and readback from both kinds of caller; check any separately claimed activation in the named client. Record partial support per target and operation.

The first useful implementation target is the complete person/machine path for a module and a pure research instrument, plus the compatible existing plugin destination. Keep the external plugin cases visible wherever an API cannot yet supply the same effect. The fixture is independent of the live register, plugin accounts, Store installation and kernel. No production dependency or reboot is part of this proposal.
