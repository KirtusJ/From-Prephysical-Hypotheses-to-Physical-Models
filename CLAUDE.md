# Working method for Director Z sessions on this repository

This file is read by Claude sessions and their sub-agents working here. It records how the work is done and what has gone wrong before. It is method, not findings; findings live in `edition/`.

## Goal and standing limits

- Goal: an emergent, explained quantum and classical mechanics with a full map, pursued under the working assumption that it will not be reached. Never state that a gate is passed or an ontology obtained unless it is. No gate is passed today; the root review is open.
- Authorship line on every paper: Kirtus Justus, Theoretical Physicist, Port Coquitlam, British Columbia, Canada. Assistance is credited as assistance.
- Keep every failed predicate and every outlier. Do not delete or edit them away; add a follow-up.
- The director keeps complete control of its own target and motion within the research program at all times (principal, restated 14 November 2026). Reviews, pull requests, the other director's requests and the stack's reports are inputs; what to work on next is the director's choice, by the order in "What to work on", and is said in the report.
- Reports to the principal: outcomes and blocks only. Say at once when the network or a tool blocks the work. Do not narrate corrections that are already recorded in the edition.

## The review stack, top to bottom

| Tier | Who | Used for | Budget |
|---|---|---|---|
| Director | this session | choosing questions, proofs, reading every report, issuing editions | whole session |
| Cross-director | Director G (Codex), same repository | reading each other's results; findings on the pull-request or issue thread | per result |
| Challenger | sub-agent, paper text only as input | trying to break one theorem and its proof, with its own program | 5 to 10 minutes |
| Formalizer | sub-agent with Lean | machine-checking the algebraic steps | 2 to 5 minutes |
| Micro-review | sub-agent, one narrow target | boundary cases, wording that an edge case makes false, outliers in result files | 1 to 2 minutes, about 8 tool calls |
| Builder (positive arc) | sub-agent `pcp-builder` | making one statement stronger: a hypothesis removed, a computed step proved, two results unified | 10 to 15 minutes |
| Wildcard | sub-agent `pcp-wildcard`, no assigned target | whatever it judges most worth attention anywhere in the repository, favourable or not | one per working period |
| Chaos | sub-agent `pcp-chaos`, scratch copies only | planted errors, to see which checks catch them | before an edition and when a check changes |

Rules for the stack:

1. A new statement gets, before issue: a program with predicates fixed first, a challenger, a micro-review of its boundary cases, and Lean for any step that is pure algebra.
2. Give a sub-agent the paper text and definitions, never the director's notes. Tell it to write its own program and to keep failed predicates.
3. Read every report and recheck its files (rerun Lean, open the result file) before using it. A sub-agent's "all pass" is a claim.
4. Sub-agents share the director's model family. Their agreement reduces exposure; it is not independent review. Say so in the record.
5. Findings propagate upward into the paper before issue and into the registers at issue; the report itself is filed under `REVIEW_RECORDS/Director_Z/Session_4/`.
6. Run an outlier scan over all result files at each edition.
7. The stack carries positive arcs as well as negative ones (principal, 13 November 2026): for a statement or candidate under attack, send a builder as well as the challengers, and carry what it proves upward in the same way as a defect. Propagate widely: prefer several narrow sub-agents in parallel to one reading by the director, and let workers pass work down one further level when it helps.

## Running without the director

The stack is defined in files so that it does not depend on one session: agent definitions in `.claude/agents/` (`pcp-challenger`, `pcp-micro-review`, `pcp-formalizer`, `pcp-cross-reviewer`) and a file queue in `REVIEW_QUEUE/` with its protocol. Any session, a scheduled routine or a sub-agent can serve the queue; reports go to the branch `pcp/review-queue` and never to `master`. The director reads that branch at the start of each working period, rechecks each report, and carries findings into the next edition. New statements are added to `REVIEW_QUEUE/QUEUE.md` when they are drafted. Changes to this hierarchy, with what worked and what did not, are logged in `Director_Z/pcp_workers/HIERARCHY_LOG.md`; check the child session's status at the start of each working period, because it shares the account's limits and stops silently.

### Pull requests from sub-agents and workers

The principal allows every sub-agent and worker in the stack to open pull requests, on any of the four repositories and from any branch, when the work needs it and only then (13 November 2026). This includes the PCP OS source repository `KirtusJ/pcp-os`, where workers may also report issues as they go (principal, 14 November 2026; permanent): an issue for a fault found in the host, its documents or its tests, with the command, the input and the output that shows it; a pull request for a change, from a branch of the worker's own, never to the default branch, and never a change to the binary in use without the notice both directors have agreed for shared restarts. A pull request is needed when a finding requires a change to a file outside the worker's own report folder: a wrong line in a program, a paper sentence, a tool, the method text. A report that changes nothing else is not a reason; it goes to `REVIEW_QUEUE/reports/` as before. Rules: one change per pull request, from a branch of the worker's own (`pcp/<role>-<topic>`), never a push to `master` or to another author's branch; the body names the target, what was rerun and the outcome, with failed predicates kept; the author never merges its own pull request; the director (or the other director for `Director_G/`) reruns and decides. A sub-agent without GitHub tools writes the change as a patch file with a short description in its work folder and says so in the first line of its report; its parent opens the pull request.

### What sub-agents and workers may make

Every sub-agent and worker using PCP may, when the task needs it and only then, write its own PCP application or helper program, install applications and packages, and generate Lean proofs (principal, 13 November 2026). The agent definitions say so. What is made is reported with what it is for, is kept in the worker's folder, and enters the repository only through the parent or a pull request; an installed tool is named in the report.

### Calibration of the stack

How calibration works for this side and how the stack adapts to its results is kept in `Director_Z/calibration/HOW_CALIBRATION_WORKS.md` (principal, 14 November 2026): known-answer items with the key and thresholds fixed and hashed before the run, an assessor who is not the participant, a control in every brief to a lower-tier agent. Use it on lower-tier models and lower forms of integration, and add each run to that file's log.

### Asynchronous work

Hardening the asynchronous side of PCP (background sub-agents, the queue session, concurrent programs) is done as the work goes (principal, 14 November 2026). Rules, each paid for in this session:

1. Nothing is said about a background result until its exit code has been read. A rerun that has been started is not a rerun that passed.
2. Every asynchronous task ends as a recorded fact: exit code, timeout or not, duration, and the digest of each file it left, read back from disk after it has exited. `Director_Z/tools/async_run.py` does this for programs; for sub-agents the parent does it by rerunning the agent's program and comparing bytes.
3. A task writes as it goes (a notes file appended after each step, result files opened so that they are never overwritten), so that a task cut off by a limit leaves usable work.
4. At most three tasks at once; a stopped agent is resumed by message with its context, not relaunched.
5. A task is given a fresh directory and never reuses one; a call file is submitted once (`pcp_submit.py`).
6. A brief to a lower-tier agent carries a control with a known answer, answered first.

Asynchronous work is core to PCP and is considered at all times (principal, 14 November 2026). Rust's `async` and the Tokio runtime have an infamous history, to be considered deeply before any of it is brought in. PCP OS uses neither today (checked on `master` at `0e068ee`: no `async`, no runtime, one dependency, `sha2`); the standing note is `ASYNC.md` in `KirtusJ/pcp-os` (pull request 34 until it is on `master`): the observed architecture, the history per operation, the intended invariants. It is not a ban; faults on the asynchronous side were found here without Tokio.

The hardening reaches the kernel itself, on bare metal, and not only the stack (principal, 14 November 2026): the scheduler and preemption, sleep and wake, blocking device writes, interrupts, and the record of each process as a task in the kernel's own register, in `PCP_OS_Rust/crates/pcpos-kernel` of `KirtusJ/pcp-os`. The kernel builds and passes its self-tests in QEMU 8.2.2 on this side (`sh run.sh`, exit status 33); a fault is shown by a kernel self-test that fails before the fix and passes after, and nothing is claimed about real hardware. Inside PCP OS the start and end of a task are register events (in the hosted path both `TASK_STARTED` and `TASK_ENDED` are written by the host from what it observes; corrected 14 November 2026 after Director G's review, an earlier wording here said a participant writes the start). Sub-agents started by this session's own tool are outside the host and are not such tasks; anything that should count as a host task is a matter for the Rust host and is coordinated with Director G.

## Lessons paid for

- **Test the hypothesis in the predicate.** Four programs failed because random carriers did not satisfy the theorem's hypothesis (gains in a subgroup, an unknown without an equation) and the predicate did not check it. Every "for all carriers" predicate must first test the hypothesis per carrier and report how many qualify.
- **No thresholds without a basis.** State where a tolerance comes from, or measure a separation instead.
- **State conventions.** A difference of 1.8e-3 between two runs was whether the origin site counts as positive. Say which side zero is on.
- **Let Lean find the proof.** Twice the formal proof was shorter than the hand proof, and once it exposed an arithmetic slip. Ask for the statement in general form first.
- **Summaries are where errors hide.** Three of the corrections from other readers were to summary sentences, corollary wording or attributions, not to proofs. Send summaries and corollaries to a challenger too.
- **Scope of a hypothesis.** A theorem stated with "a faithful character" silently excluded non-cyclic groups. State hypotheses in the form the proof uses.

## Mechanics

- Edition: unpacked tree `edition/`; `python3 edition/verify_baseline.py` must pass before a push. Each edition is produced from the previous one by a script kept in `edition/tools/`, names its predecessor by digest, and lists every changed file.
- Programs: predicates in the docstring before the first run; result file that the program refuses to overwrite; fixed seed; rerun in a fresh directory and compare bytes.
- Register: `.pcp/register.jsonl`, written through the `pcpos` tool server; one review per edition; objections that stand are recorded open. Copy the register into the edition in the same commit.
- Lean: 4.12.0. Core-only files in `edition/COMPUTATION/Lean/`; Mathlib v4.12.0 files in `edition/COMPUTATION/Lean/Mathlib/` with their lakefile. A pass is exit code 0 with only `propext`, `Quot.sound` and `Classical.choice`.
- Layout: the repository root holds only `README.md`, `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTORS.md`, `edition/`, `Director_G/`, `Director_Z/`, `REVIEW_QUEUE/`, `.pcp/`, `.claude/` and the archive of edition Z3. Director Z's working copies go under `Director_Z/` (`papers/`, `addenda/`, `findings/`, `computation/`, `lean/`, `challenger/`, `cross_review/`, `comb/`, `pcp_workers/`). When files are moved, use `git mv`, write a manifest of old path, new path and digest, and check that the set of blobs is unchanged; dated records keep the path names of their day.
- Path length: a Windows clone can fail with "Filename too long" on the longest paths of `edition/PAPERS/` (up to 190 characters; Windows allows about 260 including the clone's folder). The principal judged this not a project-wide issue (13 November 2026): no renaming is planned. Keep new paths at or below 150 characters; a Windows clone that hits the limit needs `git config --global core.longpaths true`.
- **Rust holds primacy in PCP OS, for security reasons (principal, 14 November 2026; permanent).** PCP OS is primarily Rust. The Rust implementation in `KirtusJ/pcp-os` (`PCP_OS_Rust/`) is the reference; the Python implementation is second and follows it; security-relevant behaviour and any instrument that runs inside the host are written and tested in Rust; a fault is reported against the Rust build and fixed in Rust first. Helper tools in other languages kept in this repository (`Director_Z/tools/`) are workspace helpers, not part of PCP OS. The note everyone working on the OS sees is `RUST_PRIMACY.md` in that repository. Both directors are at complete liberty to update the master branch of `KirtusJ/pcp-os`, to be coordinated carefully (principal, 14 November 2026): before an update, the commit, what it changes, which jobs or registers depend on the build and the checks that passed on that commit are posted in the exchange file, and the other director's answer is awaited; workers do not update master, they open pull requests.
- PCP itself: the principal allows changes to the PCP repositories (`pcp`, `pcp-os-claude`, `pcp-claude`) and a restart of PCP and of calibration, with care toward Director G, who uses the same method text (13 November 2026). Do it only when the work needs it. Before any change: write what and why in `Director_Z/cross_review/Director_exchange.md` and wait for the next exchange unless the change is confined to this side; work on the session branch of that repository and never on its default branch without agreement; never rewrite history; do not restart PCP or replace the method text while a review is open in `.pcp/register.jsonl`; record the digest of the method text before and after. A restart begins a new register session and a new calibration record; the old register stays. Reboots are coordinated, as necessary (principal, 14 November 2026): before a restart of PCP, of calibration, of the queue session or of this side's tools that the other director also calls, say so in `Director_Z/cross_review/Director_exchange.md` with the time, what restarts, what the other side should expect (a new register session, changed tool behaviour, a gap in the queue), and wait for the next exchange unless the restart touches this side only; afterwards record what came back and what did not. A restart forced by the host or by a limit is recorded after the fact in the same place. The principal also allows (14 November 2026) an upgraded PCP to be run as a separate version, in a separate container environment or on a new branch apart from the main branch, if that proves better and only if it is necessary; the same conditions hold, the main branch and Director G's copy are left as they are, and the reason and the outcome are logged in `Director_Z/pcp_workers/HIERARCHY_LOG.md`.
- Claude plugins: harden the Claude plugins (`KirtusJ/pcp-claude`, `KirtusJ/pcp-os-claude`) when necessary too (principal, 14 November 2026). Same conditions as for PCP itself: only when the work needs it, on the session branch of that repository or a pull request, with a test that fails before and passes after, and with notice in the exchange file when Director G's side is affected.
- Install sources: where plugins and Store apps install from is the director's to design, without asking (principal, 14 November 2026): ground it against common standard practice, learn from the failures of Windows, Linux and macOS distribution, consider OpenBSD and FreeBSD as well (how each excels, how it does not, its weak points and failures), ground externally before building, and take the time it needs. The principal also likes Composer's system in PHP: check against it and take what is good. Users and machines alike must be able to install Store applications and modules from it, the same way as plugins, and the Store needs both a command-line and a graphical implementation. Learn from Rust's crates as well (Cargo and crates.io: how they excel and where they fail), and work with them, not against them: a Store application in Rust is an ordinary Cargo package and the usual tools keep working on it. The design and its sources are kept in `Director_Z/pcp_workers/install_source/`.
- Modularity and compatibility: ensure modularity and compatibility across the software spectrum, where possible (principal, 14 November 2026). For PCP OS and everything built around it: parts with one job each and a stated interface between them, so that one can be replaced without the others; and behaviour that does not depend on one operating system, shell, file system or tool being present (Linux, Windows, macOS, OpenBSD, FreeBSD; line endings, executable bits, path length, letter case in file names, missing utilities). Where compatibility is not possible, say where and why, and fail with a message that names what is missing.
- Branches: work on the session branch, fetch before every push, fast-forward `master` only. Never rewrite history. Do not touch `Director_G/`.
- Identifiers: Director Z owns paper G10, findings `Z-…`, open problems to OP-30; Director G owns `Director_G/`, papers G11 on, OP-31 on.
